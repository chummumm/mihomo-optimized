# Mihomo Optimized Windows 桌面版

Windows 客户端使用 C# WPF 原生控件和 Fluent 主题，包含主页、代理、连接、DNS、规则、日志、配置编辑与设置。Rust 后台管理本项目的 Mihomo 二开内核、系统代理、TUN 服务和更新。Windows 界面与网页面板分别构建，网页面板继续使用原有 React 实现。

## 0.2.11 Windows TUN 创建、恢复与快速切换

配套内核为 **1.0.35**。Windows TUN 继续使用 Wintun；已核验的本产品设备可以进入原生重新创建流程，不再要求先观察到 phantom。不同 GUID 的同名接口、身份不符与查询失败继续明确拒绝，失败包含阶段、设备身份与原生错误。

客户端停止在 TUN 失败后自动改用固定备用名并重启。显式 `tun.device` 继续代表用户配置的设备名称；历史备用名映射在安全的生命周期边界退役，避免在仍运行的 TUN 上直接迁移。真实的外部同名占用仍需先停止其所属程序或由用户修改配置，客户端不按名称清理其他网卡。

当前运行健康与上次操作失败分别保存和显示。开启 TUN 失败并成功恢复普通模式时，界面明确显示 TUN 未启用和上次失败结果，不将旧冲突长期当作当前网卡占用；普通代理健康不代表 TUN 已修复。成功重试或明确关闭 TUN 后清理对应操作失败，晚到的旧状态不能覆盖新的操作结果。

仅开关 TUN 且其他配置未改变时，使用内核的局部配置接口应用完整有效的 TUN 参数，并回读确认；省去额外配置校验进程与整份节点、规则和 DNS 的重载。生成运行配置时统一内核已有的默认参数，避免首次开启时将正常补全误判为失败，或反复开关后在同源重载中无谓重建网卡；源 YAML 保持原样，显式设备名、路由和非默认参数仍严格核对。失败仍执行回滚，取消或无法确认运行状态时保留现有进程退出屏障。其他配置修改继续走原有完整校验和重载。

启动控制端口由内核自身绑定系统分配的可用端口，客户端通过本次启动标识、精确进程身份和实际地址完成交接，再进行认证和配置就绪确认。首次启动、自动恢复与内核替换使用同一路径，避免探测端口后释放再绑定的竞争；控制接口绑定失败会结束本次启动并清理资源。相同配置重载保留控制监听器。完整安装包包含支持该交接的配套内核。

模式、日志等级、端口等已有轻量更新，以及普通网络变化和相同 TUN 配置下的句柄复用保持。故障记录关联本次操作、时间和实际运行状态，报错后不需要通过反复手工枚举网卡猜测失败发生时的情况。

**请使用 0.2.11 完整安装包升级**。宿主与服务使用通信协议 v5，明确区分 TUN 请求与普通配置重载，需要同步替换原生界面、宿主、服务和配套内核。配置、订阅与用户偏好保留；独立内核更新只提供核心的设备管理修复，无法更新旧桌面的状态展示和恢复策略。Windows 原生测试覆盖创建者占用、立即关闭重建、异常退出、安装升级、内核独立更新、失败回滚和真实 TUN 转发；S3 / S4 / Modern Standby 与具体无线驱动仍需实机验证。

## 0.2.10 启动、切换与 TUN 状态修复

配套内核为 **1.0.33**。本版修复后台已经恢复健康、设置页仍保留“状态快照待刷新”旧红字的问题；运行状态提示随最新状态更新，用户操作失败的结果单独保留。首次 TUN 健康采样期间显示检查中，已就绪控制器和停止操作仍可使用；真实过期、设备不可用和持续检查失败继续显示异常。

仅切换规则 / 全局 / 直连、局域网开关、日志等级或代理端口时，后台使用内核已有的运行配置接口并回读确认，不再执行整份配置的资源准备和重载。端口实际监听成功后才切换系统代理地址；配置同步保存，失败时恢复已确认的运行状态。其他配置变化继续执行完整的配置检查与应用。

安装版在配套服务已经安装并运行时，由同一服务管理普通模式和 TUN 模式。开关 TUN 通过原内核应用配置，不再每次停止整个进程并切换宿主；首次从普通进程转入服务仍需要一次迁移。便携版的普通模式继续由用户进程管理。设备归属检查、停止优先级、服务身份校验与系统代理恢复规则继续生效。

首次启动内核时，直接由实际进程完成配置解析、资源准备与就绪检查，去掉启动前额外运行一次 `-t` 的重复解析；运行中整份重载仍保留预校验和失败恢复。新增启动阶段耗时记录，可区分界面、宿主、配置准备、进程创建和就绪等待。首次下载规则或 Geo 数据的实际耗时仍取决于资源与网络。

**请使用 0.2.10 完整安装包升级**。本版宿主与服务使用通信协议 v4，需要同步更新界面、后台、服务和配套内核。独立内核更新不能修复旧界面提示，也不能升级服务协议。保存配置并退出旧程序后覆盖安装，配置与偏好继续保留；便携用户使用完整新版目录。

安装版的服务内核日志位于 `%PROGRAMDATA%\Mihomo Optimized\service\logs`，无论当前是否开启 TUN；普通进程内核以及界面和宿主日志位于 `%LOCALAPPDATA%\Mihomo Optimized\logs`。设置页的日志目录入口按实际管理者打开对应目录。

## 0.2.9 Windows 内核独立更新

0.2.9 首次加入内核独立更新，随包内核当时为 **1.0.29**。以下更新设置沿用至当前版本，配套内核和完整安装要求以本页 0.2.11 说明为准。Windows 可以在桌面应用版本不变时独立更新内核；YAML 中已有的 `core-auto-update` 和 `core-update-interval` 由桌面后台读取并调度，使用与 Linux 等平台相同的正式内核发布源。

```yaml
core-auto-update: true
core-update-interval: 24
```

`core-auto-update` 默认关闭，`core-update-interval` 是正整数小时数，默认 24。保存并应用配置后生效；桌面程序运行期间自动检查，发现更高的正式版本后下载并安装。切换页面或收起到托盘不会中止后台任务。未启用自动更新时，仍可在配置页“内核、规则与 Geo 数据”区域点击“检查并更新”。内核行显示当前版本、检查结果和自动更新状态，资源行继续显示规则、订阅提供者和 Geo 数据的更新结果。

候选下载、SHA-256 校验和版本 / 桌面接口检查期间保留当前内核，准备完成后才短暂重启并切换。新内核启动失败时尝试恢复旧版本；停止指令取消旧更新任务，取消后的迟到结果不会重新启动内核。原本停止的内核可以更新文件，完成后仍保持停止。替换运行中的内核会中断其已有连接，应用可能需要重新连接。

安装版由 Windows 服务写入受保护的 Program Files 目录，因此独立更新需要安装并运行新版服务，即使当前没有开启 TUN。服务可以在设置页“桌面服务”区域安装，安装服务不会自动打开 TUN；便携版在自己的可写目录内更新。更新沿用原有 TUN 选择和配置。

独立内核更新不会替换宿主或服务，桌面协议升级仍需使用应用更新或完整安装包。0.2.9 使用的是协议 v3；升级到当前 0.2.11 时请按上方完整安装要求操作。

### 0.2.8 自动启停与退出原因记录

本版补齐桌面界面、后台与 Windows 服务的生命周期记录，用于追查“Wi-Fi 断开后没有操作，内核却进入停止或恢复，随后出现 TUN 冲突”这类问题。内核仍使用相同来源的 **1.0.28**；不修改内核代码、内核日志等级、TUN 恢复判断或服务通信协议。

记录覆盖后台通信失败与自动替换、实际发出的启停请求、服务接收与执行、内核启动结果及退出结果。实际请求编号和进程实例将这些步骤关联起来，各层的运行意图序号分别标注；底层通用的 `user_stop` 不再作为“用户点击停止”的唯一依据。停止记录区分停止前进程已退出、优雅退出阶段确认退出、发出强制结束后确认退出，以及退出未确认，并保留退出码和阶段耗时。

桌面端还记录只读的网络接口状态变化，并合并保留最终状态未变的操作系统网络通知及首次通知时间，便于追查瞬断后很快恢复的情况。网络观察不发出启动、停止或 TUN 重建指令；已有内核健康接口提供的 TUN 身份与状态用于关联当时的运行实例。日志使用有界异步写入和轮转，不等待磁盘完成后才处理网络变化或启停。

发生异常后，请保留故障前后同一时间段的以下文件，包括对应的轮转文件：

- `%LOCALAPPDATA%\Mihomo Optimized\logs\ui-recovery.log`：界面、后台通道与网络状态记录。
- `%LOCALAPPDATA%\Mihomo Optimized\logs\recovery.log`：桌面后台和非 TUN 内核的生命周期记录。
- `%PROGRAMDATA%\Mihomo Optimized\service\logs\recovery.log`：TUN 服务及其内核的生命周期记录。
- 同目录的 `core.log`：内核原有日志，继续遵循原来的内核日志设置。

这些记录自动保存，不需要额外按钮。记录中仅包含有限的事件类别、状态、编号和设备身份，不写入配置正文、订阅内容或控制密钥。异常发生后的恢复也需要保留，才能区分原实例恢复、重新创建和关闭 TUN 后启动。

本版是桌面侧归因与诊断补充，不能据此认定某台机器的 Wi-Fi 异常根因已经修复。自动化验收与真实 Wi-Fi 切换仍应分别说明；普通断网的目标是保留内核 PID、TUN 身份与创建次数。

### 0.2.7 升级后的 TUN 自动恢复

旧版程序退出后，Windows 仍可能保留原来的 TUN 接口。新版内核无法确认旧接口归属时会拒绝使用同名设备；例如配置中显式指定 `tun.device: utun`，更新后可能遇到 `already exists with active, foreign or unverified ownership`。这属于设备创建阶段的冲突，配置语法本身可能完全正确。

本版在正常启动、启用 TUN、重载或后台恢复遇到这类明确冲突时自动处理：确认本程序的旧内核退出后，使用稳定名称 `MihomoDesktop` 创建自己的网卡并重试，无需点击额外修复按钮。原 YAML 文件保持原样，运行名称映射保存在桌面偏好中，绑定原配置里的设备名称，并在后续启动、重载及恢复中一致应用。设置页显示配置名称和使用名称；配置中的设备名称改变后，旧名称映射不再应用。

自动恢复沿用正常的停止、取消和启动流程，恢复期间仍可停止内核，旧操作不能覆盖新的停止意图。未确认旧进程退出、配置已变化或有未保存修改时，不启动第二个内核。名称冲突只触发一次固定名称的自动恢复；如果 `MihomoDesktop` 本身冲突，会保留明确的失败原因，不循环尝试更多名称。恢复动作不按名称主动删除、接管或重命名原接口，也不会擅自开启用户已关闭的 TUN。独立内核仍保持显式设备名称和所有权检查的原有行为，配套版本继续为 **1.0.28**。

本次回归补充实际启用旧版 TUN 后的升级，以及旧版强制退出留下同名接口时的一次启动自动恢复场景。验收不点击修复按钮、不补发重试，直接验证自动恢复后的真实转发、原 YAML 字节保留及重载和重新启动后的映射。Wintun 在新建接口时可能自行清理已经退出的孤立设备，因此测试允许旧孤立实例保持原身份或已消失，但要求新接口具有独立身份；另验证仍活动的同名外部接口保留原名称与身份，以及专属名称被占用时停止尝试并保留原设备。具体通过情况以本版 Windows Actions 验收记录为准，已有停止优先级和退出清理检查继续执行。

### 0.2.6 Wi-Fi 切换、TUN 原地恢复与停止响应

配套内核更新为 **1.0.28**。普通 Wi-Fi 切换或暂时断网保留内核和 TUN；缺失的自有 TUN 地址、路由优先原地补齐。恢复结果带实例、代次和操作编号，网络抖动和丢回复不会造成重复重建或遗失失败状态。创建前只读检查已有接口名称；强制退出后的恢复只允许设备 GUID、产品标识与原生实例全部匹配，且 Windows 明确认定为非活动的设备重新创建。其他同名冲突或无法完成身份查询的情况会停止创建。

对于旧版崩溃后、无法确认归属的同名网卡残留，启动会明确报冲突。可以正常退出原持有程序，或将配置中的 `tun.device` 改为一个未使用的名称后重试。新版创建时写入独立的产品标识，自动恢复仅处理满足完整身份检查的非活动实例。

Windows 服务将只读状态、独立认证心跳和串行启停工作分开。启动资源等待、健康恢复和配置重载期间仍可读取状态并停止；停止采用统一预算，旧任务的迟到结果不能重新启动内核。界面分别显示进程存活、控制通道、TUN 健康和当前操作，状态未知不再直接显示为内核退出。主页、恢复页、托盘和搜索入口均保留恢复期间的停止操作。

请使用本版完整安装包同时更新原生界面、Rust 宿主、TUN 服务和内核。新的服务协议要求配套组件，旧服务会提示更新，不能只替换一个 EXE。安装与升级保留用户配置；回退时也应使用完整的已知版本组合。

Windows 自动验收验证真实 TUN 地址 / 路由移除后的新鲜健康观测与转发恢复，核对 PID、LUID、代次和创建次数未变；另验证原生子进程强制退出后的重建、自动重启等待资源时状态及时响应、停止在资源预算结束前完成，并且迟到结果不重新启动。CI 没有真实无线 AP 和睡眠硬件，不能代替 Wi-Fi 漫游、DHCP 变化和 S3 / S4 / Modern Standby 实机验收。旧连接可能因出口地址变化中断。

### 0.2.5 睡眠恢复、LAN 预连接与代理目标 IP

配套内核更新为 **1.0.23**。服务心跳期限改用不计睡眠 / 休眠时间的活动时钟，并绑定经过认证的宿主进程身份；恢复后重新核对实际内核 PID、认证接口、监听端口及本程序拥有的 TUN 设备、地址和路由。健康内核保留，确认局部 TUN 资源失效时才修复，网络暂未恢复或状态未知不直接触发重启。用户手动停止优先于后台恢复，旧宿主退出确认后才替换断开的本地通道。

撤回上一版 EasyTier 请求内的 15 秒准备加 5 秒连接预算，业务拨号恢复原有 5 秒期限，保留路由及并发正确性修复。改为只对 RFC1918 IPv4 / ULA IPv6 业务目标启动后台准备，覆盖 EasyTier、WireGuard / AmneziaWG、Tailscale、ZeroTier、OpenVPN；不增加节点配置，不扫描网段或重放 UDP。未知冷目标第一次连接仍可能超时，后续请求可复用原生已建立路径。

同时加入 issue #61 的可选 `proxy-force-ip`、节点 `target-ip-family` 与按域名限定的 `dns.answer-ip-family-policy`。TCP / UDP 代理目标可使用本地取得的真实 IP，规则和日志域名保留，`normal` 模式继续可用。地址族限制显式配置，不把一次失败推断为远端缺少 IPv4 / IPv6。详见[代理目标 IP](https://github.com/chummumm/mihomo-optimized/blob/mihomo-optimized-v1.0.23/docs/proxy-force-ip.md)和 [LAN 预连接](https://github.com/chummumm/mihomo-optimized/blob/mihomo-optimized-v1.0.23/docs/lan-preconnect.md)。

自动验收包括活动时钟、恢复与停止竞态、真实 Windows TUN 路由移除后修复、健康实例 PID 保留，以及宿主通道替换。CI 不等于实际设备的 S3 / S4 / Modern Standby 验收；现场睡眠恢复结果仍需以设备实测为准。

### 0.2.4 首次连接与窗口状态修复

配套内核更新为 **1.0.22**。EasyTier 保留按需启动与实例复用，将首次组网准备和 TCP 建连分开计时：组网准备最多 15 秒，目标路由就绪后 TCP 建连最多 5 秒，整次请求不超过 20 秒；调用方更短的期限继续生效，普通连接仍使用原来的 5 秒。就绪检查覆盖实际目标和可用下一跳，支持经中继转发，并修复并发启动时可能错过状态通知的问题。

Windows 主窗口在首次显示前按所在显示器的实际工作区和 DPI 调整位置、尺寸及最小尺寸，避免高缩放或较矮屏幕上标题栏超出屏幕。恢复窗口、切换显示器与工作区变化时重新检查，保留正常位置、系统最大化和贴靠操作。验收直接检查首次显示的窗口，检查前不缩窗。

配置保存成功改为约 2.5 秒的短提示，关闭编辑器或离开页面后清理，重新打开不再出现上次的绿色成功条。“仅保存，待应用”与应用失败属于配置状态，会保留到实际应用成功；从文件重新读取同一修订不会误清这些状态。

### 0.2.3 界面与动效更新

## 原生 Fluent 功能

客户端将 Fluent 设计中的布局、操作和状态处理迁移到 C# WPF。`mihomo-optimized.exe` 是原生 Windows 界面，`mihomo-desktop-host.exe` 保留配置、内核生命周期、系统代理和可信更新逻辑；受限服务及受保护目录中的内核替换由 `mihomo-desktop-service.exe` 承担，实际代理转发由 Go 编写的 `mihomo-core.exe` 完成。0.2.10 随包内核为固定来源的 **1.0.33**，安装后可独立更新至更高的正式版本；网页面板继续独立使用 React。

- **窗口与导航**：48 像素自定义标题栏、返回、窗口最小化/最大化/关闭，展开、紧凑和窄窗覆盖式导航。Windows 11 支持时使用系统 Mica 背景与 Acrylic 浮层，Windows 10 或关闭透明效果时使用同色实底。窗口仍支持原生拖动、调整大小与贴靠；高对比度和关闭动画设置由系统控制。
- **主页与托盘**：主页显示 4 个当前出口摘要，托盘显示 3 个，包含实际叶节点和延迟，点击进入对应策略组。主页提供启动/停止/重启、运行模式、系统代理、TUN、局域网和开机启动；托盘提供快速开关、流量和内核电源操作。
- **全局搜索**：Ctrl+K 搜索命令、页面、策略组、节点、设置项和规则内容，支持关键词高亮与键盘选择。设置结果滚动至具体项目并高亮，节点/组结果定位到代理页，规则结果保留原始匹配顺序并自动筛选。
- **代理**：来源→策略组→出口的实时图形拓扑、连接速率与路径动画，支持点击定位；分组展开状态持久保存，节点卡片提供延迟历史、排序、UDP 信息及逐项/批量测速，Ctrl+T 执行批量测速。提供者支持健康检查和更新，可选择切换节点时断开关联连接。
- **连接与流量**：真实 60 秒流量历史、双向速率、悬停采样，来源筛选和分组统计、排序/调整列宽、实时详情及关闭连接。保留已关闭连接时使用有界历史，内核切换后清除旧状态。
- **DNS、规则和日志**：DNS 概览、完整分钟趋势、精确筛选、50/100 条分页与跳转、上游和实际出口明细；规则集合更新和内容筛选；日志级别、暂停/继续、清空与跟随最新。DNS 分页保留内核返回的锚点与索引，兼容旧内核的游标翻页。
- **配置**：文件、URL、粘贴和拖放导入；原生 YAML 编辑器包含虚拟行号、行列/大小状态、Tab 缩进、Ctrl+S、查找、原换行格式、只读/大小限制、未保存确认和修订冲突保护。保存与重载状态分别处理，重载失败可单独重试；离线时仍可修复配置。资源更新显示真实任务、自动更新和下次调度状态。
- **设置与语言**：中文/English 即时切换，跟随系统/浅色/深色主题和系统强调色。模式、局域网、代理端口通过桌面后台保存并回读确认；测速 URL、显示偏好分别持久化。配置目录、日志目录、服务管理及可信应用更新沿用原有入口。

功能与原稿源文件的对应关系见 [原生实现对照](NATIVE-PARITY.md)。

## 下载与启动

- `mihomo-desktop-<版本>-windows-x64-setup.exe`：Windows x64 安装包。安装到 Program Files，适合日常使用及 TUN。
- `mihomo-desktop-<版本>-windows-x64-portable.zip`：解压整个目录后运行 `mihomo-optimized.exe`，适合普通系统代理使用。TUN 需要使用安装版的受保护程序路径。
- 配置与桌面设置保存在 `%LOCALAPPDATA%\Mihomo Optimized`。便携包是免安装的程序分发形式，用户数据仍保存在此目录。
- 原生界面及 .NET 运行环境均包含在安装包和便携包中，无需 WebView2 或另外安装 .NET。支持 Windows 10 1809 及更新版本的 x64 系统。

首次启动后，在配置页导入 Clash / Mihomo YAML 文件，或粘贴配置订阅地址，然后启动内核。默认示例配置只有直连规则，不能替代你自己的节点或订阅。

## 桌面操作

关闭窗口会收起到托盘；托盘可以重新打开界面、停止代理，或真正退出。退出时，程序先恢复由它设置的系统代理，再关闭配套内核。如果系统代理在运行期间被别的程序修改，会保留那个新设置。

普通系统代理不需要让整个界面以管理员身份运行。从主页或托盘首次启用 TUN 时，会先显示说明，再请求管理员授权安装受限 Windows 服务；也可以在设置页的“桌面服务”区域安装或卸载服务。服务只管理本项目的固定内核，失去桌面程序心跳后会停止其持有的内核，无论当前是否开启 TUN，防止关闭界面进程后仍遗留代理进程。

安装 TUN 服务时会为受保护安装目录中的 `mihomo-core.exe` 配置 TCP 入站防火墙例外，供 `mixed` / `system` 协议栈使用；升级保留并修复此规则，卸载服务时清理本程序规则。

TUN 使用你导入配置中的 DNS 策略，要求 `dns.enable: true`。配置里的 `tun.enable` 由桌面开关控制。Linux 的透明代理、iptables 和 TCP SYN 主动探测参数不适用于 Windows；发现不兼容项时，先在配置编辑器中修复。

## 配置与故障恢复

内核启动失败时，主界面仍可以打开配置编辑器和日志目录。保存配置使用内容修订号检查，避免覆盖另一个编辑器刚保存的文件。保存和重载是两步：保存失败不会覆盖旧文件；内核不接受重载时会保留先前运行配置。

控制端口和认证密钥由桌面程序临时生成，不从网页 URL 或浏览器存储读取。控制接口只监听本机回环地址。导入的配置不能改变此控制通道。`core-auto-update` 和 `core-update-interval` 保留在用户 YAML 中，由桌面后台调度独立内核更新；桌面管理的内核进程本身不执行二进制自替换，也不更新桌面界面或随包网页资源。

### 更新后的首次自动启动

`0.1.6` 将启动状态与耗时的内核操作分开读取。即使后台启动早于界面订阅事件，或正在检查配置、下载规则与 Geo 数据，界面也能立即读取最近状态，显示“正在启动”及准备说明。尚未取得状态、正在启动和正在停止时，不显示停止后的导入配置建议，并禁用重复启动或重启按钮；实际失败时仍保留明确错误与修复入口。

内核必须同时通过本进程身份、认证、运行状态和实际监听端口确认，宿主才会接管系统代理。就绪期间读取本地状态遇到暂时的连接中断、超时或服务端错误，会在同一操作期限内继续确认。明确的身份或认证失败、协议不兼容、实际端口不匹配仍然报错；失败清理及原有总预算保持不变。

“第一次失败、重启成功”本身不能证明 YAML 有误，也不能唯一定位到系统代理。例如，第一次下载已经保存了部分有效资源，第二次只需补齐其余资源，也会出现相同现象。实际失败时，请保留界面的完整提示和日志目录中的 `core.log`；启动最终的 fatal 错误不受 `log-level: silent` 的普通日志过滤影响。资源总预算耗尽后仍会结束该轮启动，不通过自动重置预算反复重启掩盖问题。

### 启动资源无法直连时

桌面版 `0.1.5`（配套内核 `1.0.20`）可以直接使用现有节点或代理组。在现有 YAML 顶层添加：

```yaml
resource-bootstrap:
  proxy: "Proxy"
  timeout: 180
```

这里的 `Proxy` 是原配置中组的名称。支持 `select`、`fallback`、`url-test`、`load-balance`、内置 `GLOBAL` 和嵌套组，沿用各自的选择策略、筛选、已有本地订阅和可读取的选择缓存。手动组不会因下载失败擅自切换到另一成员；自动组可以在该组范围内重试当前 GET 的失败路径。临时组没有长期健康检查，资源缓存齐全时不额外探测。

也可以把 `proxy` 写成已有具体节点名，不限 AnyTLS。若要直接指定某个订阅缓存中的节点，再加 `proxy-provider: "我的订阅"`；选组时使用组原有的 `use` 等字段。只读取已有缓存、文件、内联内容或 payload 后备，不会为取得引导节点先下载订阅。仅有订阅 URL、没有任何本地节点或有效后备时，仍需先准备节点信息。

这只处理初始化时缺少的规则、代理订阅和 Geo 资源。下载 URL、路径、缓存、ETag、校验与保存继续沿用；provider 原来显式设置的 `proxy`（包括 `DIRECT`）优先，并在同一独立引导图中解析。引导失败、空组或候选耗尽不静默转直连，后续定时刷新仍按原有更新配置工作。编辑、导入、保存和重新加载继续使用现有入口。

`timeout` 是正整数秒，默认 180。普通 provider 请求上限 60 秒、Geo 请求上限 120 秒、连接上限 10 秒，全部受本轮剩余预算约束。首次启动由实际进程完成配置解析和资源准备；运行中完整重载的预校验与应用共享同一资源预算，不重新计时。桌面操作另外预留 30 秒确认就绪、恢复与清理，服务通信再留 30 秒；默认分别为 210 秒和 240 秒，调整 `timeout` 后同步调整。

重载失败后，仅在原配置恢复且认证就绪通过时显示恢复成功。无法确认恢复时，在预留期限内清理本应用管理的内核；仍无法确认退出会显示明确错误，保留进程身份及编辑器、导入和日志入口供修复。服务命令仍串行执行，配置检查和启动中的停止操作可能需要等待本轮操作收敛。

启动不要求事先打开 Windows 系统代理。宿主先完成资源准备并确认内核身份和就绪，再根据保存的偏好开启系统代理；失败或仍在准备时不会把系统代理指向未就绪的端口。`0.1.5` 同时修复服务查询短暂失败后、重新确认运行时遗漏恢复系统代理偏好的问题。点击系统代理开关也可能触发一次内核启动，不能仅凭第二次成功判定第一次失败是由代理开关导致；具体错误保留在日志中。

公共内核在 Linux、macOS 等平台也支持同样的 YAML。完整选路优先级、组与节点链边界、预算和排查方法见[启动资源下载说明](https://github.com/chummumm/mihomo-optimized/blob/mihomo-optimized-v1.0.20/docs/resource-bootstrap.md)。

### 设置入口

主页集中提供启动、停止、重启与常用开关；配置页提供文件、URL、粘贴导入和 YAML 编辑。配置编辑保留未保存提示与修订冲突检查。

设置页“应用程序更新”区域的“检查应用更新”用于桌面程序、宿主、服务和随包组件；配置页“内核、规则与 Geo 数据”区域的“检查并更新”提交独立内核检查，并在内核运行时更新资源。内核停止时，仍可检查并更新内核文件；规则、订阅提供者和 Geo 数据更新需要正在运行的内核。配置编辑、导入和应用更新仍可使用。主页和设置页提供 TUN、系统代理、开机启动与局域网选项，托盘提供 TUN、系统代理和局域网快速开关；设置页可切换语言、主题，调整代理端口与测速地址。所有入口沿用同一后台状态。

## 更新

### 独立内核更新

YAML 中的 `core-auto-update` 和 `core-update-interval` 与 Linux 等平台使用相同含义：启用后自动检查并安装更高的正式内核版本，间隔单位为小时，默认 24；未启用时保留手动检查入口。调度由桌面后台负责，不依赖配置页面是否打开；完全退出桌面程序后不继续调度。手动和自动任务共用同一更新流程，运行中的资源更新完成后才进行内核切换。

下载源固定为本仓库正式内核的 `latest/download/version.txt`。读取版本后锁定对应发布标签，核对该标签下的 `SHA256SUMS`，只提取 Windows amd64 可执行文件，并检查候选版本和桌面管理接口。候选准备期间保留正在运行的代理，下载或验证失败不会先停止旧内核。提交阶段确认原进程退出后才替换文件，启动失败会尝试回滚；无法确认进程退出或回滚结果时保留明确错误，供用户重试或使用完整安装包修复。

安装版必须由配套服务操作受保护目录，普通权限界面不能指定任意下载源、文件路径或校验值；便携版要求程序目录可写。独立更新只支持本项目正式 Windows x64 内核，不支持其他核心、自定义下载地址、预发布版本或自动降级。安装版未安装服务时，可先在设置页安装新版服务，也可继续使用完整应用安装包更新配套内核。

独立更新只替换 `mihomo-core.exe`，保留桌面程序版本、配置与原有 TUN 开关。界面显示的是实际内核版本，可能高于随包 `build-info.json` 记载的初始内核版本；`-desktop` 打包标记不参与正式版本高低比较。

### 应用的启动检查与更新提示

每次启动桌面程序，5 秒后安排一次后台应用更新检查；发现新版本时显示可关闭的提示。从 `0.1.4` 起，内核启停、配置写入等操作繁忙时保留待检查状态，结束后再执行，不再因繁忙超过 30 秒而跳过。如果已手动检查，自动检查会被消费，并与正在进行的同一次检查共享结果。同一次启动期间，切换页面或从托盘重新显示窗口不会触发新的自动检查；退出会取消尚未发起的检查。关闭提示后，仍可在设置页的“应用程序更新”区域查看结果、手动检查或重试。

启动检查只查询新版信息。安装版在你点击安装更新后才下载、验证并启动安装程序；便携版的更新按钮打开对应发行页面，由你选择下载完整安装包或新版便携包。检查失败或超时不会中断内核启动或正在运行的代理，网络恢复后可以在设置中手动重试。

0.1.2 及更早版本需要先在设置中手动检查更新，或下载本次完整安装包完成升级，之后才具备启动后台检查功能。此检查独立于初始化资源预算，不会自动下载或安装新程序。

### 更新缓存清理（0.1.7）

应用内更新将安装包、构建证明文件和安装监护程序副本暂存在 `%LOCALAPPDATA%\Mihomo Optimized\updates` 下由程序创建的 32 位随机十六进制子目录。`0.1.7` 在每次启动界面后从后台检查这些目录，也在更新正常完成或失败收尾时尝试整目录回收，兼容 `0.1.6` 及更早版本留下的此类缓存。

从下载开始到安装监护结束都有跨进程使用保护；清理新旧缓存前，还会检查所有已知文件是否被占用，使用中的目录会保留。存在待回收项时，后台每 2 秒重试占用或删除失败的目录；空闲时每 30 秒检查。崩溃或断电留下的缓存会在下次启动界面后继续处理。

清理仅针对可识别的应用更新目录：非随机目录、含未知文件、重解析点（例如符号链接或目录联接）或硬链接的目录会保留，不跟随链接删除。手动下载的安装包和用户配置不在清理范围内。

### 从旧桌面版本升级

升级到 0.2.9 时，需要通过完整安装包同步更新服务通信协议 v3。先从托盘退出旧程序再覆盖安装；独立更新内核不能代替这次服务和宿主升级。便携用户应使用完整新版便携目录，不混用旧宿主或其他组件。

原生客户端保留 0.1.7 和 0.1.2 对“先卸载再安装”后出现 `Unable to stop the Mihomo desktop service` 的修复。旧卸载器可能删除主程序和内核、留下仍被占用的服务助手；新版安装器直接查询并停止 Windows 中登记的服务，不再执行这个残留旧助手。服务已不存在时继续安装，服务正在停止时等待完成，并等待旧助手文件解除占用后再替换。无法完成时会显示具体阶段与系统错误码。

正常卸载应用时，服务助手也会一起卸载：先退出主界面、停止并移除服务及本程序的防火墙规则，再等待助手退出并确认助手文件删除成功，随后删除其余程序文件。若助手仍被占用且等待超时，卸载会报告具体错误并中止，保留主程序与内核供重试；用户配置保留。

如果旧版升级已在这里中断，退出仍在运行的 Mihomo，直接重新运行当前版本完整安装包即可修复程序文件；不需要删除用户配置目录。

新版保留 0.1.1 的 TUN 错误 5 修复，并补齐保留身份句柄所需的进程查询、退出等待和令牌身份查询权限。权限仅授予登记的用户；界面与服务仍核验路径、SYSTEM 身份和进程存活，不授予终止、内存读写、句柄复制或令牌修改权限。

先从托盘退出旧程序，再运行新版完整安装包。原生安装包继续使用原安装目录和开始菜单入口；覆盖安装会停止旧服务、替换程序并启动新服务；仅替换文件或重开界面不能保证旧服务已更新。若安装时选择先卸载，首次开启 TUN 需要重新批准一次服务安装。安装完成后普通双击启动程序即可。

### 更新范围与验证

设置中的应用更新统一更新界面、宿主、服务及随包内核，应用更新包必须通过本仓库指定 GitHub Actions 工作流的 OIDC / Sigstore 构建签名验证；使用随包提供的官方 GitHub CLI 验证器离线验签，无需用户登录 GitHub。独立内核更新使用前述固定 HTTPS 来源、SHA-256 校验和候选接口检查。规则、订阅提供者和 Geo 数据仍通过内核的原有更新入口管理。

安装版可以在设置中安装更新。便携版的更新按钮打开对应发行页面：请下载完整安装包，或先退出程序再解压新版便携包，用户配置会保留。安装更新失败时会记录错误并尝试重新打开应用；若安装文件已部分写入，请使用完整安装包修复。

桌面版使用独立的 `mihomo-desktop-v*` 标签。它不会替代服务端内核发布使用的 GitHub latest 标记。没有可升级版本时，设置中的检查结果会显示当前版本。

`SHA256SUMS` 可用于核对下载完整性。`build-info.json` 记录桌面、UI、内核版本和确切来源提交；同一 Release 中的 `.sigstore.json` 提供安装包及便携包的构建证明。构建证明与 Windows Authenticode 发布者签名是两种不同机制；本发行未使用 Windows Authenticode 发布者证书签名。

## 从源码构建

使用 Windows x64、Visual Studio C++ Build Tools、.NET SDK 10.0.402、NSIS 3.11、Rust 1.99.1 和项目使用的 MetaCubeX Go 1.26 工具链。桌面构建不需要 Node.js 或 WebView2；网页面板独立构建时仍使用 Node.js 22 和 pnpm 8.15.9。

1. 检出 `clash-dashboard` 分支，将 `desktop/core.json` 指定提交检出到 `core-src`。
2. 运行 `python scripts/prepare-desktop.py --core-dir core-src`，准备固定版本的内核、服务与构建证明验证器。
3. 运行 `python scripts/build-native-desktop.py`，生成 WPF 原生程序、Rust 后台及 NSIS 安装包。
4. 运行 `python scripts/package-desktop.py`，生成与安装版逐文件一致的便携包，产物位于 `artifacts/desktop`。

原生界面源码位于 `src-windows`，后台源码保留在历史目录 `src-tauri` 中，但其 Cargo 依赖和运行程序均已移除 Tauri。`desktop/app.json`、WPF 工程和 Cargo 的桌面版本必须一致。普通网页构建继续使用 `pnpm build`。

完成第 2 步后，开发时可运行 `python scripts/build-native-desktop.py --skip-installer --run`，构建包含后台和内核的完整原生目录并启动界面；此模式无需 NSIS。`pnpm desktop:dev` 是同一命令的别名。直接 `dotnet run` 只编译界面，不会自动准备这些配套程序。

## 验证与源码

0.2.9 的独立内核更新验证范围包括配置调度与版本比较、下载大小和 SHA-256 校验、ZIP 内容约束、取消后的候选清理，以及文件替换、确认和回滚。Windows 验证使用真实旧版本内核和正式发布的候选，检查准备阶段保留原运行进程，并覆盖受保护服务的更新流程。具体通过情况以本次提交的 Actions 记录和报告为准。

保留应用更新缓存回归，覆盖旧缓存自动回收、文件和程序映像占用时保留、释放占用后的后台重试，以及用户文件保护。测试仅在一次性 Windows runner 中创建的应用更新目录内构造夹具。

首次启动正向验收使用已保存的运行偏好、合法配置和没有缓存的慢资源：不发送手动启动 / 重启命令，准备期间多次读取状态必须及时返回 `starting`，界面不显示停止或导入修复提示，系统代理保持 DIRECT，资源准备完成后自动就绪。另保留坏 YAML 的自动启动失败回归，并验证就绪探测的暂时失败可以恢复、永久错误与总超时仍明确失败。

`.github/workflows/windows-desktop.yml` 包含 Windows 编译、真实内核 HTTP 代理回环测试，以及真实 0.1.1 卸载后重新安装的回归：主动让旧助手在卸载时残留，确认旧助手会报错，再验证新版安装器能完成升级并保留用户配置。还会在服务运行时覆盖安装，执行新版应用的完整卸载，确认助手与其余程序文件、服务、防火墙规则和卸载注册记录均已移除而配置保留，然后再安装真实已发布的 0.1.7，运行旧服务并直接覆盖升级到原生版，确认完整运行文件哈希、唯一的 64 位卸载记录、服务所有者和用户配置均正确。随后使用真实 WPF 界面与 Windows UI Automation 检查配置修复、启动期间控件状态、系统代理恢复、服务和隔离 TUN 流量。界面使用同一用户的中等完整性令牌，管理员组设为仅拒绝、没有启用调试特权；服务测试同时核对有限查询可用、终止及读写内存等更高权限被拒绝。测试在一次性 GitHub Windows runner 中运行，未覆盖独立标准用户账户；不同物理网卡、睡眠恢复、企业网络策略和长期运行仍需要实际机器验证。
