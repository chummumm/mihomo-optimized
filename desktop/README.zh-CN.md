# Mihomo Optimized Windows 桌面版

主界面沿用本仓库的 React UI，包含连接、DNS、代理、规则、日志和配置编辑页面。桌面宿主为 Tauri 2，配套的是本项目的 Mihomo 二开内核。

## 下载与启动

- `mihomo-desktop-<版本>-windows-x64-setup.exe`：Windows x64 安装包。安装到 Program Files，适合日常使用及 TUN。
- `mihomo-desktop-<版本>-windows-x64-portable.zip`：解压整个目录后运行 `mihomo-optimized.exe`，适合普通系统代理使用。TUN 需要使用安装版的受保护程序路径。
- 配置与桌面设置保存在 `%LOCALAPPDATA%\Mihomo Optimized`。便携包是免安装的程序分发形式，用户数据仍保存在此目录。
- 界面使用 Microsoft WebView2。安装包在缺少运行环境时自动下载引导安装；离线电脑请先准备 WebView2 Runtime。

首次启动后，在设置中导入 Clash / Mihomo YAML 文件，或粘贴配置订阅地址，然后启动内核。默认示例配置只有直连规则，不能替代你自己的节点或订阅。

## 桌面操作

关闭窗口会收起到托盘；托盘可以重新打开界面、停止代理，或真正退出。退出时，程序先恢复由它设置的系统代理，再关闭配套内核。如果系统代理在运行期间被别的程序修改，会保留那个新设置。

普通系统代理不需要让整个界面以管理员身份运行。启用 TUN 时，设置页面会安装受限 Windows 服务并请求一次管理员授权；服务只管理本项目的固定内核。可在设置中卸载服务。服务失去桌面程序心跳后会停止 TUN 内核，防止关闭界面进程后仍遗留接管网络的进程。

安装 TUN 服务时会为受保护安装目录中的 `mihomo-core.exe` 配置 TCP 入站防火墙例外，供 `mixed` / `system` 协议栈使用；升级保留并修复此规则，卸载服务时清理本程序规则。

TUN 使用你导入配置中的 DNS 策略，要求 `dns.enable: true`。配置里的 `tun.enable` 由桌面开关控制。Linux 的透明代理、iptables 和 TCP SYN 主动探测参数不适用于 Windows；发现不兼容项时，先在配置编辑器中修复。

## 配置与故障恢复

内核启动失败时，主界面仍可以打开配置编辑器和日志目录。保存配置使用内容修订号检查，避免覆盖另一个编辑器刚保存的文件。保存和重载是两步：保存失败不会覆盖旧文件；内核不接受重载时会保留先前运行配置。

控制端口和认证密钥由桌面程序临时生成，不从网页 URL 或浏览器存储读取。控制接口只监听本机回环地址。导入的配置不能改变此控制通道，也不能启用内核自己的二进制或 UI 更新。

### 更新后的首次自动启动

`0.1.6` 将启动状态与耗时的内核操作分开读取。即使后台启动早于界面订阅事件，或正在检查配置、下载规则与 Geo 数据，界面也能立即读取最近状态，显示“正在启动”及准备说明。尚未取得状态、正在启动和正在停止时，不显示停止后的导入配置建议，并禁用重复启动或重启按钮；实际失败时仍保留明确错误与修复入口。

内核必须同时通过本进程身份、认证、运行状态和实际监听端口确认，宿主才会接管系统代理。就绪期间读取本地状态遇到暂时的连接中断、超时或服务端错误，会在同一操作期限内继续确认。明确的身份或认证失败、协议不兼容、实际端口不匹配仍然报错；失败清理及原有总预算保持不变。

“第一次失败、重启成功”本身不能证明 YAML 有误，也不能唯一定位到系统代理。例如，第一次下载已经保存了部分有效资源，第二次只需补齐其余资源，也会出现相同现象。实际失败时，请保留界面的完整提示和日志目录中的 `core.log`；启动最终的 fatal 错误不受 `log-level: silent` 的普通日志过滤影响。资源总预算耗尽后仍会结束该轮启动，不通过自动重置预算反复重启掩盖问题。

### 启动资源无法直连时

桌面版 `0.1.5`（配套内核 `1.0.20`）可以直接使用现有节点或代理组。在现有 YAML 顶层添加：

```yaml
resource-bootstrap:
  proxy: "Proxy"
  timeout: 180
```

这里的 `Proxy` 是原配置中组的名称。支持 `select`、`fallback`、`url-test`、`load-balance`、内置 `GLOBAL` 和嵌套组，沿用各自的选择策略、筛选、已有本地订阅和可读取的选择缓存。手动组不会因下载失败擅自切换到另一成员；自动组可以在该组范围内重试当前 GET 的失败路径。临时组没有长期健康检查，资源缓存齐全时不额外探测。

也可以把 `proxy` 写成已有具体节点名，不限 AnyTLS。若要直接指定某个订阅缓存中的节点，再加 `proxy-provider: "我的订阅"`；选组时使用组原有的 `use` 等字段。只读取已有缓存、文件、内联内容或 payload 后备，不会为取得引导节点先下载订阅。仅有订阅 URL、没有任何本地节点或有效后备时，仍需先准备节点信息。

这只处理初始化时缺少的规则、代理订阅和 Geo 资源。下载 URL、路径、缓存、ETag、校验与保存继续沿用；provider 原来显式设置的 `proxy`（包括 `DIRECT`）优先，并在同一独立引导图中解析。引导失败、空组或候选耗尽不静默转直连，后续定时刷新仍按原有更新配置工作。编辑、导入、保存和重新加载继续使用现有入口。

`timeout` 是正整数秒，默认 180。普通 provider 请求上限 60 秒、Geo 请求上限 120 秒、连接上限 10 秒，全部受本轮剩余预算约束。配置检查消耗的时间会从正式启动的资源预算中扣除，不重新计时。桌面操作另外预留 30 秒确认就绪、恢复与清理，服务通信再留 30 秒；默认分别为 210 秒和 240 秒，调整 `timeout` 后同步调整。

重载失败后，仅在原配置恢复且认证就绪通过时显示恢复成功。无法确认恢复时，在预留期限内清理本应用管理的内核；仍无法确认退出会显示明确错误，保留进程身份及编辑器、导入和日志入口供修复。服务命令仍串行执行，配置检查和启动中的停止操作可能需要等待本轮操作收敛。

启动不要求事先打开 Windows 系统代理。宿主先完成资源准备并确认内核身份和就绪，再根据保存的偏好开启系统代理；失败或仍在准备时不会把系统代理指向未就绪的端口。`0.1.5` 同时修复服务查询短暂失败后、重新确认运行时遗漏恢复系统代理偏好的问题。点击系统代理开关也可能触发一次内核启动，不能仅凭第二次成功判定第一次失败是由代理开关导致；具体错误保留在日志中。

公共内核在 Linux、macOS 等平台也支持同样的 YAML。完整选路优先级、组与节点链边界、预算和排查方法见[启动资源下载说明](https://github.com/chummumm/mihomo-optimized/blob/mihomo-optimized-v1.0.20/docs/resource-bootstrap.md)。

### 设置入口

顶栏保留唯一的启动 / 停止入口，设置页保留重启和刷新状态。编辑配置、重新加载已保存配置归入同一配置区域；已经位于设置页时不再显示重复的设置跳转按钮。

“桌面应用”区域中的“检查应用更新”用于桌面程序和配套内核；“规则与 Geo 数据”区域中的“检查并更新资源”使用正在运行的内核更新资源。内核离线时，资源更新显示不可用原因，配置编辑、导入和应用更新仍可使用。TUN、系统代理、登录启动与语言继续各保留一个可编辑设置。

## 更新

### 启动检查与更新提示

每次启动桌面程序，5 秒后安排一次后台应用更新检查；发现新版本时显示可关闭的提示。从 `0.1.4` 起，内核启停、配置写入等操作繁忙时保留待检查状态，结束后再执行，不再因繁忙超过 30 秒而跳过。如果已手动检查，自动检查会被消费，并与正在进行的同一次检查共享结果。同一次启动期间，切换页面或从托盘重新显示窗口不会触发新的自动检查；退出会取消尚未发起的检查。关闭提示后，仍可在设置中的“桌面应用”区域查看结果、手动检查或重试。

启动检查只查询新版信息。安装版在你点击安装更新后才下载、验证并启动安装程序；便携版的更新按钮打开对应发行页面，由你选择下载完整安装包或新版便携包。检查失败或超时不会中断内核启动或正在运行的代理，网络恢复后可以在设置中手动重试。

0.1.2 及更早版本需要先在设置中手动检查更新，或下载本次完整安装包完成升级，之后才具备启动后台检查功能。此检查独立于初始化资源预算，不会自动下载或安装新程序。

### 更新缓存清理（0.1.7）

应用内更新将安装包、构建证明文件和安装监护程序副本暂存在 `%LOCALAPPDATA%\Mihomo Optimized\updates` 下由程序创建的 32 位随机十六进制子目录。`0.1.7` 在每次启动界面后从后台检查这些目录，也在更新正常完成或失败收尾时尝试整目录回收，兼容 `0.1.6` 及更早版本留下的此类缓存。

从下载开始到安装监护结束都有跨进程使用保护；清理新旧缓存前，还会检查所有已知文件是否被占用，使用中的目录会保留。存在待回收项时，后台每 2 秒重试占用或删除失败的目录；空闲时每 30 秒检查。崩溃或断电留下的缓存会在下次启动界面后继续处理。

清理仅针对可识别的应用更新目录：非随机目录、含未知文件、重解析点（例如符号链接或目录联接）或硬链接的目录会保留，不跟随链接删除。手动下载的安装包和用户配置不在清理范围内。

### 从旧桌面版本升级

0.1.7 保留 0.1.2 对“先卸载再安装”后出现 `Unable to stop the Mihomo desktop service` 的修复。旧卸载器可能删除主程序和内核、留下仍被占用的服务助手；新版安装器直接查询并停止 Windows 中登记的服务，不再执行这个残留旧助手。服务已不存在时继续安装，服务正在停止时等待完成，并等待旧助手文件解除占用后再替换。无法完成时会显示具体阶段与系统错误码。

正常卸载应用时，服务助手也会一起卸载：先退出主界面、停止并移除服务及本程序的防火墙规则，再等待助手退出并确认助手文件删除成功，随后删除其余程序文件。若助手仍被占用且等待超时，卸载会报告具体错误并中止，保留主程序与内核供重试；用户配置保留。

如果旧版升级已在这里中断，退出仍在运行的 Mihomo，直接重新运行 0.1.7 完整安装包即可修复程序文件；不需要删除用户配置目录。

新版保留 0.1.1 的 TUN 错误 5 修复：服务只向登记的用户授予有限进程查询权限，界面与服务的路径及用户身份验证仍然执行，解决普通权限界面开启 TUN 时无法验证 SYSTEM 服务进程的问题。

先从托盘退出旧程序，再运行新版完整安装包。覆盖安装会停止旧服务、替换程序并启动新服务；仅替换文件或重开界面不能保证旧服务已更新。若安装时选择先卸载，首次开启 TUN 需要重新批准一次服务安装。安装完成后普通双击启动程序即可。

### 更新范围与验证

设置中的应用更新统一更新界面、宿主及配套内核。更新包必须通过本仓库指定 GitHub Actions 工作流的 OIDC / Sigstore 构建签名验证；使用随包提供的官方 GitHub CLI 验证器离线验签，无需用户登录 GitHub。规则、订阅提供者和 Geo 数据仍通过内核的原有更新入口管理。

安装版可以在设置中安装更新。便携版的更新按钮打开对应发行页面：请下载完整安装包，或先退出程序再解压新版便携包，用户配置会保留。安装更新失败时会记录错误并尝试重新打开应用；若安装文件已部分写入，请使用完整安装包修复。

桌面版使用独立的 `mihomo-desktop-v*` 标签。它不会替代服务端内核发布使用的 GitHub latest 标记。没有可升级版本时，设置中的检查结果会显示当前版本。

`SHA256SUMS` 可用于核对下载完整性。`build-info.json` 记录桌面、UI、内核版本和确切来源提交；同一 Release 中的 `.sigstore.json` 提供安装包及便携包的构建证明。构建证明与 Windows Authenticode 发布者签名是两种不同机制；本发行未使用 Windows Authenticode 发布者证书签名。

## 从源码构建

使用 Windows x64、Visual Studio C++ Build Tools、WebView2、Node.js 22、pnpm 8.15.9、Rust 1.99.1 和项目使用的 MetaCubeX Go 1.26 工具链。

1. 检出 `clash-dashboard` 分支，运行 `pnpm install --frozen-lockfile`。
2. 将 `desktop/core.json` 指定提交检出到 `core-src`。
3. 运行 `python scripts/prepare-desktop.py --core-dir core-src`。
4. 运行 `pnpm exec tauri build --ci --target x86_64-pc-windows-msvc --bundles nsis`。
5. 运行 `python scripts/package-desktop.py`，产物位于 `artifacts/desktop`。

开发界面使用 `pnpm desktop:dev`，开发地址固定为 `http://localhost:3000`。普通网页构建继续使用 `pnpm build`。

## 验证与源码

本轮新增更新缓存回归，覆盖旧缓存自动回收、文件和程序映像占用时保留、释放占用后的后台重试，以及用户文件保护。测试仅在一次性 Windows runner 中创建的应用更新目录内构造夹具。

首次启动正向验收使用已保存的运行偏好、合法配置和没有缓存的慢资源：不发送手动启动 / 重启命令，准备期间多次读取状态必须及时返回 `starting`，界面不显示停止或导入修复提示，系统代理保持 DIRECT，资源准备完成后自动就绪。另保留坏 YAML 的自动启动失败回归，并验证就绪探测的暂时失败可以恢复、永久错误与总超时仍明确失败。

`.github/workflows/windows-desktop.yml` 包含 Windows 编译、真实内核 HTTP 代理回环测试，以及真实 0.1.1 卸载后重新安装的回归：主动让旧助手在卸载时残留，确认旧助手会报错，再验证新版安装器能完成升级并保留用户配置。还会在服务运行时覆盖安装，执行新版应用的完整卸载，确认助手与其余程序文件、服务、防火墙规则和卸载注册记录均已移除而配置保留，然后重新安装。随后检查 WebView2 界面、配置修复、系统代理恢复、服务和隔离 TUN 流量。界面使用同一用户的中等完整性令牌，管理员组设为仅拒绝、没有启用调试特权；服务测试同时核对有限查询可用、终止及读写内存等更高权限被拒绝。测试在一次性 GitHub Windows runner 中运行，未覆盖独立标准用户账户；不同物理网卡、睡眠恢复、企业网络策略和长期运行仍需要实际机器验证。
