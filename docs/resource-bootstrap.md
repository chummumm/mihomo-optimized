# 启动时下载规则、订阅和 Geo 数据

内核 `1.0.19` 新增 `resource-bootstrap`，`1.0.20` 将出口扩展到已有代理组。当缺少的资源无法直连下载时，内核可以在完整业务规则和 DNS 就绪之前，借助配置中已有的节点或组完成初始化下载。Windows、Linux、macOS 等平台使用相同实现；Windows 桌面版 `0.1.5` 配套通用组引导，并协调宿主和服务的等待时间。

这一设置只决定初始化资源请求的出口和时间预算。现有资源 URL、文件路径、有效缓存、ETag、订阅元数据、格式验证与保存方式继续使用，配置编辑器和导入流程不变。

## 使用已有代理组

例如原配置已经有名为 `Proxy` 的组，在配置顶层添加：

```yaml
resource-bootstrap:
  proxy: "Proxy"
  timeout: 180
```

组定义继续放在原来的 `proxy-groups` 中，成员继续取自原来的 `proxies` 和 `proxy-providers`，不增加第二套组配置。支持当前内核已有的四类组、组的嵌套和内置 `GLOBAL`；已被普通内核移除的 `relay` 不在支持范围内。

| 组类型 | 初始化下载时的选择 |
| --- | --- |
| `select` | 沿用可读取的既有选择、`default-selected` 与原有默认成员逻辑；下载失败不擅自改选另一个直接成员 |
| `fallback` | 保留候选顺序，在当前请求中避开已失败的路径并尝试后续可用候选 |
| `url-test` | 使用有界探测结果和原有延迟 / 容差逻辑选点，当前请求失败后在该组内重新选择 |
| `load-balance` | 保留原有 `strategy`，按实际资源请求目的地选择成员；失败排除只属于当前请求 |

`select` 选择了一个自动组时，该子组仍可按自身策略回退，但不会跳到手动组的另一个直接成员。原有 `use`、`include-all`、筛选和排除规则继续生效；订阅只读取现成的本地缓存、文件、内联或 payload 后备，不为构造引导组先更新订阅。

当 `profile.store-selected` 启用时，引导读取现有选择缓存，不写入新的选择记录。当前进程已经打开缓存时复用只读事务；其他进程占用文件、缓存不可读取时有界返回并使用组的默认选择，不长时间等待数据库锁。

资源需要下载时才构造临时代理和执行必要的一次性探测，不启动引导组的长期健康检查。探测地址失败不会单独成为资源下载的硬门槛，仍可用真实资源请求判断候选。连接、TLS、HTTP 状态或响应体读取失败时，只在允许自动选择的组内重试幂等 GET；所有尝试共用原请求和整轮时间预算。资源内容的格式校验继续由原 provider / Geo 加载器完成。

每次资源请求需要补做的整棵组探测合计最多使用 5 秒，并且不超过该请求剩余预算的四分之一；每个节点同时受原组的 `timeout` 约束。探测子预算耗尽后继续尝试真实资源下载，为下载保留时间。同一轮已经完成探测的组不反复测速；资源请求本身或整轮期限耗尽时仍立即取消。

不存在的引用、依赖环或筛选后没有可用本地成员会明确失败。不会因为空组默认的 `COMPATIBLE` 后备而悄悄直连；需要直连时必须在配置中明确选择相应出口。选组时不填写 `resource-bootstrap.proxy-provider`，由组自己已有的 `use` 等字段描述订阅来源。

## 使用已有静态节点

在原配置顶层、与 `proxies` 和 `rules` 同级添加：

```yaml
resource-bootstrap:
  proxy: "下载节点"
  timeout: 180
```

`下载节点` 必须是现有 `proxies` 中的具体节点名称。无需复制节点密码或另外保存一份节点设置；原协议、TLS、SNI 和传输参数继续由原节点适配器处理。

功能不限定 AnyTLS。它复用内核已有的出站适配器和 TCP / UDP 拨号能力；能否成功仍取决于该节点协议、服务器、网络和本地依赖是否可用。

## 使用已有订阅缓存中的节点

节点在代理订阅中时，明确填写对应 provider：

```yaml
resource-bootstrap:
  proxy-provider: "我的订阅"
  proxy: "下载节点"
  timeout: 180
```

`我的订阅` 必须存在于当前配置的 `proxy-providers` 中，且内核已经有可读取的本地内容。支持 `http` provider 的原有缓存、`file` provider 的原路径，以及 `inline` provider 的内联内容；原 provider 配置了 `payload` 后备时，继续沿用该后备。节点筛选、排除、覆盖配置、格式转换和最终名称沿用该 provider 原来的解析规则；请填写处理后的节点名。相对路径仍按内核的数据目录解释。

引导解析不会为了获得这个节点先更新订阅，也不会启动该临时 provider 的健康检查。第一次使用、尚无订阅缓存或有效内联后备时，需要先成功导入 / 下载一次订阅，或选用静态节点。仅有一个无法直连的订阅 URL、没有任何本地节点信息时，程序无法自行推导出代理服务器和凭证。

节点的 `dialer-proxy` 依赖也必须能从本地代理图解析；依赖链会检查缺失引用和循环，不通过尚未下载的订阅递归取得缺失节点。错误会指出无法解析的依赖，而不是一直重试。

## 哪些请求使用这个出口

| 场景 | 行为 |
| --- | --- |
| 初始化缺少的 GeoIP / GeoSite / ASN 等实际依赖 | 使用本轮引导出口，继续原来的内容校验和保存 |
| HTTP rule-provider 首次需要下载，未单独指定 `proxy` | 使用本轮引导出口 |
| HTTP proxy-provider 首次需要下载，未单独指定 `proxy` | 使用本轮引导出口 |
| provider 已显式设置 `proxy` | 优先在本轮独立引导图中解析该节点或组，包括显式 `DIRECT`；即使未设置默认引导出口也生效 |
| 已有可用缓存或本地 / 内联 provider | 使用原有本地内容，不强制重新下载 |
| 内核运行后的定时刷新和手动资源更新 | 使用原有更新流程和出口设置 |
| 普通网页、应用、DNS 等业务流量 | 按原 `rules`、策略组和 DNS 配置工作 |

省略 `resource-bootstrap.proxy` 不会凭空选择某个代理。需要特定 provider 在后续更新时也固定使用代理，仍应填写它原来的 `proxy` 字段；`resource-bootstrap` 不替代长期更新策略。

节点地址的初始解析使用系统 DNS，避免依赖尚未加载的业务规则或 Geo 数据；它不沿用业务 DNS 的规则选路。引导拨号不把原节点的域名改写成 IP，也不更改 SNI；接口、路由标记和出站防回环约束随实际拨号保留。系统 DNS 无法正确解析节点服务器时，需要先修复系统解析，或使用带有正确 TLS / SNI 设置的 IP 节点。

具体引导节点或手动组所选路径失败时，本次请求会报告失败；自动组可在自己的可用候选范围内重试。候选全部失败后不会静默改走直连。设置不能让所有节点均失效或完全断网变成可用网络。

## 时间预算

`timeout` 使用正整数秒，省略时为 `180`。不要写 `180s`、`"180"`、小数、负数或 `0`。只配置 `timeout`、不指定 `proxy` 是有效的：预算生效，出口仍使用原有策略。整个 `resource-bootstrap` 省略或设为 `null` 时也使用默认预算；对象内显式 `timeout: null` 则是配置错误。下列时间分别约束同一流程中的不同层级：

| 范围 | 默认上限 | 如何相互约束 |
| --- | ---: | --- |
| 建立下载连接 | 10 秒 | 也受请求剩余时间限制 |
| 普通 provider 下载 | 60 秒 | 也受本轮资源剩余时间限制 |
| Geo 数据下载 | 120 秒 | 也受本轮资源剩余时间限制 |
| 一轮初始化资源请求 | 180 秒 | 所有初始化请求共用，不逐个重置 |
| Windows 配置检查和启动 / 重载操作 | 210 秒 | 资源预算之外预留 30 秒，用于就绪确认、恢复与清理 |
| Windows 桌面与服务通信 | 240 秒 | 比宿主操作多留 30 秒通信余量 |

例如，配置检查已消耗 45 秒，Windows 正式启动最多再获得约 135 秒资源下载时间，不会重新取得 180 秒。单个 Geo 请求也只能使用它的 120 秒上限与本轮剩余时间中的较小者。

调整 `resource-bootstrap.timeout` 时，Windows 宿主和服务等待上限随之调整为资源预算加 30 秒、加 60 秒。增加总预算不会自动增加单个 provider 的 60 秒或单个 Geo 请求的 120 秒上限。

超时并不表示所有缓存都无效。已有可用缓存继续按原规则处理；无可用缓存的资源依赖是否导致加载失败，仍遵守原来的资源类型和配置校验规则，不用空规则集冒充下载成功。

## Windows 设置和错误恢复

在原有配置编辑器中添加上述 YAML，使用已有的保存与重新加载操作即可。无需安装第二套下载程序，也不新增一个需要与 YAML 同步的节点设置表单。

桌面宿主把剩余预算传给配置检查与正式内核，服务启动同样采用该预算。配置检查输出会提取有上限的阶段诊断；失败时仍可以打开编辑器、重新导入配置和查看日志。

系统代理不是内核启动或引导资源下载的前置条件。宿主先确认内核身份与就绪，再根据用户保存的偏好开启系统代理；下载或启动失败时不将系统代理提前指向尚未就绪的内核。服务状态短暂查询失败后，只有重新确认运行状态，才恢复该偏好。

重载失败后，恢复原运行配置必须在同一操作期限内完成；只有恢复请求成功且内核重新认证就绪，才显示恢复成功。期限耗尽或无法确认恢复时，宿主在预留期限内清理自己管理的内核；如果仍无法确认进程退出，会保留进程身份并明确报告，不把不确定状态显示为正常运行或已停止。保存到磁盘的配置继续遵循原编辑器规则，不会借此增加另一套保存事务。

当前 Windows 服务命令按顺序执行。正在配置检查或启动时，停止命令可能需要等待当前操作收敛；这次预算控制不等于给每个初始化阶段新增即时中断接口。

## 命令行和外部宿主

普通使用只需配置 YAML。需要让多个阶段共用外部期限的宿主，可以进一步限制单次初始化：

```sh
mihomo -t -d /path/to/data -f /path/to/config.yaml -resource-bootstrap-timeout=137.25s
```

参数使用 Go duration 格式，必须大于零。实际资源上限取该值和 YAML 预算的较小者；它不能放大 YAML 中的上限。命令行的启动上限不会永久套用到以后每次重载。

控制 API 的 `PUT /configs` 支持可选查询参数 `resource-bootstrap-timeout=137.25s`；原有调用不需要新增该参数。加载同时受请求上下文约束，请求取消或期限到达后，不应继续无期限下载。对已发生的配置应用，外部宿主仍需通过就绪与运行状态确认结果，不能把客户端断开等同于完整回滚。

## 常见排查

| 现象 | 检查项 |
| --- | --- |
| 提示找不到引导节点 | 静态节点名称、provider 筛选 / 覆盖后的名称，以及显式选择的 provider 是否一致 |
| 指定订阅但缓存不存在 | 先准备订阅缓存，或改用已配置的静态节点 |
| 提示依赖循环 / 缺少组或节点 | 检查组和 `dialer-proxy` 的引用，让依赖能从本地节点与已有订阅内容解析 |
| `select` 没有自动换到其他节点 | 手动组保持选择；需要自动回退时让它选择原有的 `fallback` 等自动组 |
| 空组或缺少本地订阅内容 | 检查过滤条件、现有缓存及 payload，或在原组中提供可用静态节点 |
| 仍按 DIRECT 下载 | 检查对应 provider 是否显式设置了 `proxy: DIRECT` |
| 资源下载超时 | 检查引导节点、服务器域名解析、资源地址与网络；仅在网络确实较慢时增加总预算 |
| 核心已停止，但可以编辑配置 | 这是故障恢复入口；修复 YAML 或节点后重新启动 |
| 运行后定时刷新走了别的出口 | 这是原有更新策略；为该 provider 配置长期使用的 `proxy` |

安装包版本、来源和校验方法见[发布与更新](releases.md)。Windows 桌面源码和使用说明位于 [`clash-dashboard`](https://github.com/chummumm/mihomo-optimized/tree/clash-dashboard/desktop)。
